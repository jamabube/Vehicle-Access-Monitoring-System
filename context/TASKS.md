- [x] **Rate limiting on sensitive endpoints (2026-09-09)** — Closed manuscript §1.2.2 objective 8 ("rate limiting and traffic filtering to reduce excessive or unauthorized requests and improve resistance to flooding attacks"), which the Security Design table also lists and Chapter IV's test plan expects to verify. The RFID ingestion API previously had **no throttling whatsoever**; login already had `RateLimiter` usage via `LoginRequest::ensureIsNotRateLimited()`. Added two named limiters in `AppServiceProvider::configureRateLimiting()`: `rfid-ingestion` (default 120/min, `RFID_RATE_LIMIT_PER_MINUTE`, **keyed on the device's `X-Rfid-Api-Key`** so one misbehaving reader cannot starve the others, falling back to IP for unauthenticated junk) and `login` (10/min per email+IP). Applied as `throttle:rfid-ingestion` **before** `rfid.hmac` in `routes/api.php`, so a flood is shed cheaply without paying for signature verification and a DB lookup on every junk request, and as `throttle:login` on the login POST. Both limiters **write the rejection to `system_logs`** so throttling events surface in the System Logs report next to the other security events — objective 9's half of the same story; that logging is itself wrapped in try/catch, since the point of a limiter is to shed load, not add work under pressure. Covered by `tests/Feature/RateLimitingTest.php` (6 tests: within-limit accepted, flood → 429 with nothing stored, the security event recorded, **one flooding reader does not block another**, the limiter running before signature verification, and login throttling). Suite now **124 passed / 11 pre-existing failures**.
